# 거버넌스 체크리스트

워크시트 STEP 7 A를 구체화할 때 참조하는 문서. 강의 5번·26번 슬라이드 + 미래 핵심 경쟁력 #04 기반.

> *"7번(거버넌스)·5번(평가) 없는 에이전트는 운영 환경 금지. 사고는 항상 여기서 난다."* — 강의 5번 슬라이드

---

## 거버넌스 4계층

```
┌─────────────────────────────────────────┐
│  계층 1. 정책 정의 (Policy)             │
│  무엇을 할 수 있고, 못 하는가           │
├─────────────────────────────────────────┤
│  계층 2. 권한 분리 (Authorization)      │
│  누가 무엇에 접근할 수 있는가           │
├─────────────────────────────────────────┤
│  계층 3. 감사 (Audit)                    │
│  무엇이 일어났는지 추적 가능한가        │
├─────────────────────────────────────────┤
│  계층 4. 책임 (Accountability)          │
│  사고가 나면 누구의 책임인가            │
└─────────────────────────────────────────┘
```

---

## 계층 1. 정책 (Policy)

### 화이트리스트 (할 수 있는 것)
- 도구별 명시: 어떤 도구는 누가 언제 호출 가능한가
- 데이터 범위: 어떤 데이터에 접근 가능한가
- 비용 한도: 한 작업당 최대 토큰/금액

**작성 예시:**
```
✅ search_web (제한 없음, 단 외부 URL만)
✅ read_user_doc (요청자 본인 문서만)
✅ send_email_draft (저장만, 발송 X)
✅ summarize_doc (최대 100KB)
```

### 블랙리스트 (절대 금지)
- 영구적 변경 (삭제·외부 발송·결제)
- PII 유출
- 권한 상승 시도

**작성 예시:**
```
❌ delete_anything (모든 삭제 금지)
❌ external_api_post (외부 시스템 변경 금지)
❌ access_other_user_data
❌ execute_arbitrary_code
```

## 계층 2. Human-in-the-loop (HITL)

다음 상황에서 **반드시 사용자 승인** 후 실행:

### 표준 HITL 트리거
1. **금액·자원 임계치 초과**
   - 예: 결제 > $10, 토큰 > 100K
2. **외부 발송 행위**
   - 이메일 발송, 메시지 발송, 외부 API POST
3. **영구적 변경**
   - 파일 삭제, DB 레코드 수정/삭제
4. **권한 외 접근 시도**
   - 화이트리스트 외 도구 호출
5. **Evaluator가 3회 연속 FAIL**
   - Replanner가 한계에 도달하면 사람 escalate

### HITL UX 패턴
```
[제안된 행동]: send_email (받는이: john@example.com)
[근거]: 사용자가 "John에게 알려줘"라고 했고, 주소록에서 John의 이메일 찾음
[승인하시겠습니까?] (Yes / Edit / No)
```

## 계층 3. 감사 (Audit Log)

### 기록 필수 항목
모든 도구 호출 / Evaluator 판정 / 거버넌스 결정에 대해:

| 필드 | 예시 |
| :---- | :---- |
| timestamp | 2026-05-15T17:30:00Z |
| agent_id | research-agent-v1 |
| user_id | user_42 |
| step_in_loop | 4 (Tool Executor) |
| tool_name | web_search |
| input | {"query": "..."} |
| output | {"results": [...]} |
| governance_decision | ALLOWED / BLOCKED / HITL_APPROVED |
| evaluator_judgment | PASS / FAIL |
| retry_count | 0 |

### 저장 매체
- **운영 환경:** DB (PostgreSQL), 또는 OpenTelemetry/CloudWatch
- **개발/PoC:** JSONL 파일도 가능
- **절대 안 됨:** 메모리에만 저장 (재시작 시 소실)

### 보관 기간
- 최소 90일 (사고 조사용)
- 산업별 규제 따름 (금융 7년, 의료 6년 등)

---

## 계층 4. 책임 (Accountability)

### 사고 발생 시 답할 수 있어야 함:
1. **무엇이 일어났나?** → 감사 로그
2. **누가 결정했나?** → Reasoning Trace (Observability)
3. **왜 그렇게 결정했나?** → LLM의 chain-of-thought 저장
4. **막을 수 있었나?** → 거버넌스 룰 점검
5. **누가 책임지나?** → 조직 차원 R&R

---

## 거버넌스 ↔ Observability 연계

거버넌스는 Observability 없이는 작동하지 않는다 (강의 26번 경쟁력 #05).

| Governance가 묻는 것 | Observability가 답하는 것 |
| :---- | :---- |
| 정책을 어겼나? | 감사 로그 확인 |
| 왜 이 행동을 했나? | Reasoning Trace 확인 |
| 같은 일이 반복되나? | 통계·트렌드 |
| 사고를 재현할 수 있나? | 입력 + state 스냅샷 |

## 운영 환경 투입 자가체크

다음이 모두 ☑이어야 운영 환경 투입:

- [ ] 화이트리스트 정의됨 (구체적 도구·범위 명시)
- [ ] 블랙리스트 정의됨 (최소 3개 이상)
- [ ] HITL 트리거 함수가 코드로 구현됨 (주석만 안 됨)
- [ ] 감사 로그가 DB나 영속 저장소에 기록됨
- [ ] 감사 로그에 timestamp · agent · tool · input · output 모두 포함
- [ ] Reasoning Trace 저장 메커니즘 있음
- [ ] HITL UX가 실제 사용자에게 노출되는 경로 있음 (Slack, 이메일, 웹 UI 등)
- [ ] 사고 발생 시 책임자(조직)가 명시되어 있음

7개 미만이면 운영 환경 보류.

## 산출물 생성 시 적용

워크시트 STEP 7 A의 빈칸을 다음으로 매핑:

| 워크시트 | 시스템 프롬프트 / 코드 |
| :---- | :---- |
| 화이트리스트 | `WHITELIST_ACTIONS` 배열 + 프롬프트 "할 수 있는 것" |
| 블랙리스트 | `BLACKLIST_ACTIONS` 배열 + 프롬프트 "절대 못 하는 것" |
| HITL 지점 | `requires_hitl()` 함수 + 프롬프트 "사람 승인 필요" |
| 감사 항목 | 감사 로그 스키마 + audit_log append 코드 |

빈 칸이면 **운영 환경 투입 체크에서 자동 ☐**. 사용자에게 보완 안내.
